# Publishing GNOME Shell Extension

This guide outlines the process of packaging, registering, and distributing the **UNIM typefix** GNOME Shell extension.

## 1. Prerequisites

Before packaging, ensure the core logic and CLI tool are built and bundled correctly.

- **Rust Environment**: Must be installed to build `unim-cli`.
- **GNOME Shell**: Development tools like `glib-compile-schemas` (usually part of `libglib2.0-dev`).
- **Zip Utility**: To create the distribution package.

## 2. Packaging Process

Since this extension uses a hybrid approach with a Rust binary (`unim-cli`), the packaging process includes building the binary for the target architecture.

### Automatic Packaging
We provide a `Makefile` to automate this process:

```bash
make pack
```

**What this does:**
1. Builds `unim-cli` in release mode.
2. Compiles GSettings schemas (`gschemas.compiled`).
3. Copies all required files (metadata, extension logic, schemas, and binary) into a temporary structure.
4. Creates a ZIP file named `unim-typefix@from104.github.io-<version>.zip`.

### Manual Packaging Checklist
If you need to package manually, ensure the ZIP contains:
- `extension.js`, `vkbd.js`, `prefs.js`: Core logic.
- `metadata.json`: Extension metadata (UUID, version, shell compatibility).
- `schemas/`: Directory containing `gschemas.compiled`.
- `bin/`: Directory containing the compiled `unim-cli` binary.

## 3. Registering & Distribution

The official way to distribute GNOME Shell extensions is via [extensions.gnome.org (EGO)](https://extensions.gnome.org/).

### Step-by-Step Submission
1. **Create an Account**: Sign up at [extensions.gnome.org](https://extensions.gnome.org/).
2. **Upload Package**: Go to the "Add yours" or "Upload" section.
3. **Submit ZIP**: Upload the ZIP file generated by `make pack`.
4. **Review Process**:
   - Your extension will be reviewed by the GNOME Shell team for security and code quality.
   - **Note**: Since our extension includes a binary (`unim-cli`), the reviewers may ask for the source code or a clear explanation of what the binary does. Ensure `IMPLEMENTATION.md` or `README.md` is clear about this.
5. **Approval**: Once approved, the extension will be live and searchable by users.

## 4. Maintenance

- **Version Updates**: Change the `"version"` field in `metadata.json` before every new release.
- **Shell Compatibility**: Test with new GNOME Shell versions (e.g., 47, 48) and update the `"shell-version"` array in `metadata.json`.
- **Multi-Architecture**: Consider providing separate packages or a universal package if supporting ARM64 (see the architecture detection section in `README.md`).

---

> [!IMPORTANT]
> Because this extension bundles a standalone binary, it is highly recommended to provide a link to the GitHub repository in the description so users and reviewers can verify the source code.
